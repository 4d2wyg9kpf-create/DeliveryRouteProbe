# 배송경로 0.21.0 · iPhone / iPad

**0.21.0 / 빌드 42**, iOS 18 이상. Bundle ID `kr.deliverytools.routeprobe`, 설치 이름 `DeliveryRoute`를 유지합니다.

**입지분석 → 표준 대상·고정 기준으로 점수 평가**에서 일부 평가대상지를 표준 대상으로 선택하고, 항목별 원자료를 입력한 뒤 기준분포를 확인·확정합니다. 확정한 표본과 평균·표준편차를 새 평가대상지에도 적용하므로 대상을 추가해도 기존 점수가 움직이지 않습니다. 전체 평가 항목의 자동 수집은 아직 구현 전이며 이번 버전은 원자료 직접 입력, 기준 확정, 점수 계산·버전 보관을 제공합니다.

표준 대상 구성을 변경하면 **기준 갱신·전체 평가지 점수 재계산**으로 새 기준을 확인·확정합니다. 모든 대상의 현재 점수가 새 기준으로 바뀌며 동일 조건의 원자료는 재사용합니다. 이전 기준 버전은 보관하여 다시 적용하거나 비교할 수 있습니다.

신규 인허가 목록을 입지분석에서 분리해 **신규업소** 탭으로 바로 엽니다. 대전 인허가의 조회 기간·업종 선택, 결과 검색, 제외 주소 관리, API 설정을 같은 탭에서 사용합니다. 조회 중 다른 탭이나 제외 주소 화면으로 이동해도 작업을 이어가며 **조회 중단** 버튼으로 취소합니다. 기존 공공데이터 키·활용승인·사용량과 제외 주소 보관함을 함께 사용합니다.

**거래처 목록 → 거래처 찾기**에서 상호·주소·저장 폴더명으로 즉시 검색합니다. 띄어쓰기를 다르게 입력해도 찾을 수 있고, 여러 검색어를 함께 입력하면 모두 포함한 거래처를 표시합니다. 기본은 **상호순**이며 **기존 순서**로 바꿀 수 있습니다. 정렬 선택은 다음 실행에도 유지하고 출발지·최종 도착지 선택 목록에도 적용합니다. 검색 결과 밖의 이번 배송 선택도 보관하며 숨겨진 선택 개수를 표시합니다. 검색·정렬은 전체 거래처 목록이나 배송 설정의 저장 순서를 바꾸지 않습니다.

업체 공유문의 도로명주소 뒤에 괄호 없는 **건물명·층·호수**가 붙으면 주소가 빠지던 문제를 수정했습니다. 전체 주소 문구를 보관하고, 건물번호까지의 도로명주소는 형식 확인에만 사용합니다. 선택 좌표는 공유 링크의 HTTP 응답에서 그대로 읽으며 주소를 다시 좌표로 변환하지 않습니다.

네이버 공유문 앞의 이름이 주소여도 **그 주소로 좌표를 대신 변환하지 않습니다.** 주소·업체 핀의 공유 링크는 HTTP 이동 응답에 포함된 선택 지점 좌표를 읽습니다. 좌표가 없는 장소·목록 링크는 보이는 장소 확인 화면에서 읽습니다. 공유 핀의 좌표를 확인하지 못하면 건물 대표 좌표를 저장하지 않습니다. **공유 주소 핀은 주소가 같으면 좌표·공유 URL·이름이 달라도 중복으로 판단해 기존 항목을 갱신합니다.** 갱신 시 이번 링크에서 확인한 선택 좌표와 원래 링크를 보관합니다. API 키와 기존 목록의 저장 형식은 유지합니다.

신규 인허가의 네이버 확인은 **상호명을 넣지 않고 도로명주소의 건물번호까지만** 검색합니다. 층·호수·건물명·괄호 안 동 정보는 검색어에서 제거하며, 건물 부번호와 지하 여부는 유지합니다. 도로명주소 공란과 업태구분명·위생업태명의 **푸드트럭·백화점·편의점**을 모든 신규 인허가 결과에서 제외합니다. 결과에 업태를 표시합니다.

**신규업소 → 제외 주소 관리**에서 백화점·축제행사장 등의 도로명 건물 주소를 추가하거나 휴지통으로 제거합니다. 결과의 **이 건물 주소 제외**로 바로 등록할 수도 있습니다. 등록한 건물의 **제과점영업·일반음식점·휴게음식점**을 층·호수와 관계없이 제외하며, 주소의 시·구·도로명·본번호·부번호·지하 여부를 대조합니다. `1`이 `10` 또는 `1-1`과 같은 주소로 취급되지 않습니다. 제외 주소 변경은 현재 결과에 바로 적용되어 API를 다시 호출하지 않습니다. 목록은 별도 Application Support 파일에 원자적으로 저장하며 다시 실행하거나 같은 앱으로 업데이트한 뒤에도 유지합니다.

공공데이터 조회 전의 시각 확인 오류를 수정했습니다. API 루트의 HEAD 응답에 Date가 없어서 조회 전체가 막히던 문제를 해결합니다. 키가 없는 HTTPS 시각 요청은 NAVER 홈페이지와 공공데이터포털을 사용하며 HEAD에서 시각을 읽지 못하면 GET과 다른 호스트를 순서대로 확인합니다. 오래된 캐시·리디렉션·시각 역행은 거부합니다. 업소 응답의 누락되거나 오래된 Date 헤더 때문에 정상 결과를 버리지 않습니다. 기존 인증키·사용량 보관 형식과 한도 차단은 유지합니다. 키·활용승인을 먼저 확인하여 미설정 상태에는 설정 안내를 표시합니다.

## 기기 간 공유

네이버·티맵·공공데이터의 **설정 → 기기 간 공유 → 공유 폴더 선택**에서 iCloud Drive의 같은 폴더를 아이폰과 아이패드에서 각각 한 번 선택합니다. 연결 시 기존 API 키, 배송 거래처, 인허가 제외 주소, API별 사용량을 병합하고 이후의 수정·삭제를 공유합니다. 최초 권한 선택은 기기별로 필요하며 재실행 시 저장한 폴더 접근 권한을 복원합니다. 폴더를 옮겨 권한을 읽지 못하면 다시 선택합니다.

공유 파일은 선택한 폴더 아래 `DeliveryRouteShare`에 기기별로 저장됩니다. 다른 기기의 파일을 덮어쓰지 않고 항목별 수정 순번과 삭제 기록을 병합합니다. 같은 항목을 오프라인에서 동시에 바꾼 경우 논리 순번과 기기 식별자로 결정한 한 버전으로 수렴합니다. API 키와 거래처 주소가 공유 파일에 포함됩니다. 키는 공개 소스·로그·검증 보고서에는 넣지 않습니다.

사용량은 키·API·일/월 기간별 기기 호출 기록을 합산합니다. 수동으로 입력한 외부 총 사용량은 중복 합산하지 않으며 이후 요청은 그 총량에 추가합니다. 실패·중단 요청과 서버 차단도 공유하고 기존 한국시간 초기화와 한도 차단을 유지합니다. 현재 배송의 선택·물량·차량 치수는 기기별로 유지합니다.

앱을 다시 열 때, 실행 중 15초마다, 변경 뒤, API 요청 전 공유 폴더를 확인합니다. 폴더 읽기나 보관함 쓰기가 실패하면 기존 데이터를 보존하고 공유 상태 확인이 필요한 API 요청을 보류합니다. iCloud는 즉시 반영이나 기기간 예약 잠금을 제공하는 방식이 아니므로 마지막 잔여량을 여러 기기에서 동시에 사용하는 상황을 완전히 방지할 수 없습니다. 서버 제한이 우선합니다. 실제 iPhone/iPad의 iCloud 동기화는 사용자 기기에서 확인해야 합니다.

## 네 개의 탭

- **네이버검색**: 검색어·주소·공유 링크에서 장소 이름, 주소, WGS84 좌표를 가져옵니다. 저장할 곳을 **티맵 거래처 목록 / 입지 평가대상지 목록** 중에서 선택합니다.
- **티맵최적화**: 전체 거래처 중 이번 배송지만 체크하고 출발지·최종 도착지를 따로 선택합니다. 배송 날짜·출발 시각·배송 작업시간·가능 시간대를 설정한 뒤 API로 최적화합니다. 결과 요약·지도·방문 순서를 같은 탭 상단에 표시합니다.
- **입지분석**: 평가대상지를 따로 보관하고 주변 업체·시설 경로를 조회합니다. 일부 표준 대상의 원자료로 고정한 기준분포에 따라 점수를 계산합니다.
- **신규업소**: 대전 신규 인허가·영업 목록을 기간·업종별로 조회하고 업소명·주소·업종·업태로 검색합니다. 제외 주소 관리와 인허가 API 설정을 여기서 엽니다.

적재 배치·물건 수량·로컬 배송계획 계산·운행 안내 화면은 탭에서 제외했습니다. 기존 거래처·API 키·설정·계획 파일은 보존하며 기존 적재 계산을 새 화면에서 실행하지 않습니다. 티맵 경로 결과를 보기 위해 별도의 배송계획 검증 버튼을 누를 필요가 없습니다.

## 네이버 검색과 공유 링크

업체 검색은 공식 NAVER 지역 검색 API, 주소 변환은 NAVER Cloud Maps Geocoding을 사용합니다. 검색 결과는 최대 5곳이며 이름·주소·좌표를 확인한 뒤 한 곳 또는 결과 전체를 선택한 목록에 저장합니다.

공유한 `naver.me`, NAVER 지도 장소 링크, 저장 폴더 링크를 붙여넣어 가져옵니다. 공유한 주소·업체 핀은 링크의 선택 지점 좌표를 확인하고, 좌표 없는 장소 링크는 장소 확인 화면을 열고, 목록 링크는 전체 항목 수를 대조한 뒤 장소별 상세 정보를 순서대로 읽어 선택한 목록으로 저장합니다. 공유 주소 핀은 주소가 같은 기존 항목을 갱신하고, 등록 업체는 같은 장소 ID의 기존 항목을 갱신합니다. 완료·실패 개수를 표시하며 중단해도 완료된 저장은 보존합니다. 지도 중심 좌표를 장소 좌표로 추측하지 않습니다. 일반 장소 확인 화면에 정확한 좌표가 없으면 읽은 주소를 공식 API로 변환할 수 있지만, 공유 핀은 건물 대표 좌표로 대체하지 않습니다.

공유한 주소 핀은 단축 링크의 HTTP `Location` 응답에 포함된 `appMenu=location` / `menu=location`, 전체 주소, `lng` / `lat`를 함께 검증해 원래 정밀도로 읽습니다. 브라우저·지도 렌더링·주소 변환 API를 사용하지 않으며 API 키나 무료 사용량도 필요하지 않습니다. 원본 공유 링크와 이동 응답을 함께 보관하고, 배송계획에 연결하기 전에 같은 HTTP 방식으로 다시 확인합니다. 좌표 없는 응답, 지도 중심, 중복 좌표, 출처가 다른 이동은 추측하지 않고 오류로 표시합니다. 자동 이동을 중단하고 응답마다 출처를 확인하며 최대 6회·25초로 제한합니다.

업체 공유의 `pinType=site` 형식은 주소 필드 없이 장소 ID·업체명·선택 좌표를 전달할 수 있습니다. 업체 핀도 브라우저나 주소 변환 없이 읽고 원래 장소 ID와 좌표를 보관합니다. 응답에 주소가 없을 때에는 공유문 전체의 도로명주소를 표시용 메타데이터로 보관합니다. 공유문의 업체명과 응답의 업체명이 다르면 연결하지 않습니다. 주소를 붙여넣었는지와 무관하게 좌표는 HTTP 응답에서만 가져옵니다. 링크만 붙여넣어도 이름·좌표는 읽으며, 주소가 없다는 안내를 표시합니다. 저장·다시 확인할 때도 선택 좌표와 원본 공유 주소를 보존합니다.

좌표를 포함하지 않은 장소 상세 링크와 개인 저장목록은 NAVER 웹 문서를 사용하며 웹 화면을 표시합니다. 네이버검색의 숨겨진 웹뷰는 제거했습니다. 개인·비공개 목록은 로그인 또는 공유 권한이 필요하고, NAVER 문서 구조 변경 시 읽기가 실패할 수 있습니다. 실제 개인 폴더의 읽기는 사용자 계정에서 확인해야 합니다.

두 목록은 독립적으로 보관합니다. 평가대상지에 저장한 곳이 자동으로 배송 거래처에 추가되지 않습니다. 평가대상지와 거래처는 각각 삭제할 수 있습니다. 실제 배송 정차 위치는 건물 좌표와 다를 수 있으므로 거래처 선택 시 확인합니다. 이번 배송은 최대 30곳입니다. 티맵은 고정된 최종 도착지가 필요하며 출발지 복귀 또는 목록의 다른 장소를 선택합니다.

### 0.18.1 · 검색 엔터 · 현재시각 출발 · 링크 좌표 수정

네이버검색의 검색어·주소 입력에서 Enter/검색 키가 검색 버튼과 같은 동작을 수행합니다. 한국어 조합 입력을 먼저 확정하며, 빈 입력과 처리 중 반복 입력은 요청을 추가하지 않습니다. 공유 링크 입력도 Enter로 가져올 수 있습니다.

티맵최적화는 출발시간을 현재시각으로 하는 옵션을 기본으로 켭니다. 요청 버튼을 누를 때 기기의 현재시각을 한국시간 날짜·분으로 변환해 확정하고, 요청 후 결과의 출발시각을 유지합니다. 옵션을 끄면 날짜와 시·분을 직접 지정할 수 있습니다.

지도 좌표 편집(거래처·평가대상지·시설·단지)과 티맵 하역 위치에 네이버지도 공유 링크 입력을 추가했습니다. 링크 좌표 적용 후 기존 저장 버튼으로 확정합니다. 단축 링크의 선택 핀은 HTTP 응답의 정확한 좌표를 사용하고, 등록 장소 링크는 해당 장소 ID의 선택 좌표를 읽습니다. 이름·주소·원본 자료는 수정하지 않으며 주소 대표점이나 지도 중심으로 대체하지 않습니다. 목록 링크는 좌표 편집에서 받지 않습니다.

공동주택 원본 수집은 시도·시군구·법정동 선택 범위에 맞춰 하위 법정동을 처리합니다. 신규단지 상세 수집과 미완료 상세 이어서 수집 버튼을 `신규단지 추가·미완료 상세 수집` 하나로 통합했으며, 목록 확인 전용 버튼은 유지합니다. 전국 수집도 사전 단지 목록 확인 없이 실행할 수 있습니다.

수집 중 표시하는 `지역명 · 상세 완료/전체`의 앞 숫자는 행 번호가 아니라 저장된 실제 상세 완료 건수입니다. 기존 완료 건수에서 시작해 성공적으로 저장할 때 한 건씩 늘며, 현재 법정동의 전체 건수는 수집 시작 시 고정합니다. 수집 범위의 법정동 완료 수와 현재 법정동의 상세 수를 분리하고, 실패·중단을 성공 완료로 세지 않습니다.


### 0.19.0 · 길찾기 제공자 선택·모바일 웹·PC 크기 자동 조회

자동차는 네이버 API·카카오 API·네이버 웹·카카오 웹을 선택합니다. 도보와 대중교통은 별도 이동방식이며 두 지도 서비스의 모바일 웹을 사용합니다. 자동차 웹은 내부 WKWebView를 1,280×700 이상으로 렌더링하고 PC 응답을 요청합니다. 네이버 검색 브라우저에도 PC 크기 보기 버튼을 추가하고, 링크 좌표 확인 웹 화면은 PC 크기로 열어 선택 요소의 렌더링 범위를 확보합니다. 아이폰에서는 가로로 밀어 전체 웹 화면을 볼 수 있고, 판독 결과는 앱의 좁은 화면에 별도로 줄바꿈해 표시합니다. 화면 밖에 렌더링된 DOM도 읽지만 숨겨진 이전 결과나 아직 로드되지 않은 내용은 사용하지 않습니다.

출발·도착 좌표는 등록된 WGS84 값을 공식 경로 링크에 전달합니다. 네이버는 최종 URL의 좌표·이동방식과 선택 모드를 비교하고, 카카오는 새 웹뷰의 공식 좌표 링크가 리디렉션한 좌표 표식을 고정한 뒤 주소 입력·숨은 폼·이동방식과 함께 검증합니다. 화면의 픽셀·지도 축척·걸음 수·운임·개별 구간 시간을 거리·총시간으로 읽지 않습니다. 여러 번 안정적으로 표시된 결과만 저장하며 150초 안에 확인하지 못하면 오류와 남은 구간을 표시합니다. 제공자를 자동 변경하거나 현재 출발 값으로 조용히 대체하지 않습니다.

시간 지정 자동차 조회는 카카오 미래 운행 API 또는 두 서비스의 PC 웹 ‘나중에 출발’을 사용합니다. 네이버 웹은 10분, 카카오 웹은 5분 단위이며 카카오 웹 출발일은 오늘부터 1년 이내입니다. PC 웹의 미래 예상 창은 지정 시각의 시간만 제공하고 본래 카드의 거리·시간은 현재 경로 값이므로, 미래 결과의 거리 칸은 비워 두고 현재 경로 참고 거리를 별도 보관합니다. 네이버 Directions 5는 현재 교통 기준이고 출발시각·최단거리 옵션을 제공하지 않으므로 지원하지 않는 조합은 선택할 수 없습니다.

네이버 자동차 API는 Maps 키와 Directions 5 권한을 사용합니다. 대표 계정의 월 무료 60,000회는 Geocoding 월 3,000,000건과 분리해 요청 전에 보관하며 기기 간 사용량도 서비스별로 합산합니다. 기존 키·사용량·SQLite 결과 보관함은 유지합니다. CSV에는 제공자, 이동방식, 조회·출발시각, 시간 기준, 웹 원문, 참고 거리를 함께 내보냅니다. 대중교통 화면에 총거리가 없으면 빈칸으로 보관합니다.

카카오 현재 자동차 다중 출발·목적지는 최대 30곳을 한 API 요청으로 유지합니다. 그 밖의 여러 구간은 최대 500곳을 같은 고정 조건으로 순서대로 조회합니다. 저장이 끝난 구간에서만 완료 숫자가 증가하고, 화면에 머문 동안 중단한 구간부터 이어서 조회할 수 있습니다. 앱이 배경으로 가거나 화면을 벗어나면 중단합니다. 앱 재실행 후에는 저장 결과를 확인해 대상 구간을 다시 선택합니다.

### 0.20.0 · 백그라운드 공동주택 수집·단지 진행률·예상 시간

공시가격 수집 작업을 화면 대신 보관함이 소유합니다. 다른 탭이나 단지 화면으로 이동해도 계속하며, iOS 26 이상에서는 사용자가 수집/재개 버튼을 눌렀을 때 Continued Processing 작업으로 등록해 다른 앱 사용·화면 잠금 중에도 처리합니다. 시스템이 실행을 거절하면 짧은 백그라운드 실행으로 전환하고, 만료·취소 시 요청을 멈춥니다. 앱을 강제 종료하거나 시스템이 중단하면 무제한으로 실행되지 않으며, `보관된 수집 이어서 하기`로 재개합니다. 작업 범위와 확정된 단지 목록은 SQLite에 저장합니다.

선택 범위의 모든 단지 목록을 먼저 확인합니다. 이 단계에서는 전체 수가 미확정이므로 임의의 완료율을 표시하지 않습니다. 목록 확정 후 진행바와 바로 아래 숫자는 `완료 단지/전체 대상 단지`입니다. 이미 저장한 상세는 완료 수에 포함하고 실패는 포함하지 않으며, 재개 시 같은 목록을 사용해 분모가 바뀌지 않습니다. 최근 20건의 실제 처리 시간(최소 3건)을 기준으로 남은 시간과 예상 완료 시각을 표시합니다. 서버 대기·단지별 상세 양 차이로 예상 시간은 달라질 수 있습니다.

단지 하나를 저장할 때 전체 지역의 JSON·검색 색인을 재작성하던 처리를, 한 단지의 원본·검색 행·완료 수를 함께 저장하는 트랜잭션으로 바꿉니다. 저장이 성공한 뒤에만 숫자가 증가합니다. JSON은 10건마다 또는 지역 종료·중단 때 별도 작업에서 저장하고, 그 전에 앱이 종료되어도 저널을 재생합니다. 검색·정렬·JSON 인코딩은 화면 스레드 밖에서 실행하고, 목록은 최대 3초에 한 번 갱신하며 진행률·예상 시간은 별도 표시 영역에서 갱신합니다. 공유 폴더의 원본 인코딩도 별도 작업으로 처리합니다.

모든 공시가격 클라이언트가 같은 요청 스케줄러를 사용합니다. 한 번에 한 요청만 보내고 시작 간격은 최소 350ms로 유지하며, 이전의 단지별 500ms 추가 대기는 제거합니다. 중복 동 요청과 완료 상세 재요청을 줄입니다. HTTP 429·서버 오류는 Retry-After와 지수 대기를 적용하며 최대 3회로 제한합니다. 긴 대기·403·접근 확인 화면·반복 오류에서는 수집을 보류합니다. 이 간격이 서비스의 공식 허용량이나 차단 방지 보장은 아닙니다. 사용자 API의 기존 쿼터는 그대로 유지합니다.

검증: `bash scripts/test_housing_kakao.sh`에서 서로 다른 지역 규모의 전체 단지 진행률, 예상 시간, 중단·재실행·저널 복구, 원본·사용자 보정 유지, UI 갱신 횟수와 제한 응답을 검사합니다. IPA는 Xcode 26 이상으로 빌드하며 실제 기기의 장시간 잠금·배터리·시스템 중단 조건은 별도 기기 확인이 필요합니다.
